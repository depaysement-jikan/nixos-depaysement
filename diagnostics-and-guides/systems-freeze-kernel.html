Why shinobu keeps hard-freezing

Friday, 14 Aug 2026 Booted kernel 6.18.44 Repo develop @ 695889c Reviewed live, on-host

Bottom line: the configuration has one clearly broken habit — the kernel is completely unpinned and floats to whatever nixpkgs-unstable ships on the day of each rebuild, which is how this box ended up running a days-old 6.18.44. Beyond that, most of the specific config bugs from the earlier session are already fixed. The amdgpu-only theory got weaker while this review was running: a second oops happened today, in a completely unrelated subsystem, with the same corrupted-pointer signature. That points at something broader than one driver.

Active right now — this boot is already degraded

While reviewing the repo I checked this session's own journalctl -k -b 0, since this happens to be running directly on shinobu. The current boot (started 13:12) took a kernel oops at 13:18:14, about 37 minutes before this report — general protection fault, probably for non-canonical address 0x6cb3447e1cffc, in lookup_swap_cgroup_id via unmap_vmas, immediately followed by a second fault in rcu_note_context_switch. The kernel logged Fixing recursive fault but reboot is needed! and tainted itself (D).

Unlike the Aug 12 incident, Hyprland itself is still alive and the desktop is usable — this is what let the review continue. But the machine is in the same kind of degraded state that preceded the Aug 12 hard freeze: dozens of kworkers, systemd-coredump, and even a stray sudo invocation are stuck in uninterruptible sleep.

1 — Kernel floats with zero pin highest priority

No host defines boot.kernelPackages — checked all four hosts, whole repo grep is empty.

Nothing in this repo ever sets boot.kernelPackages, so every host — including shinobu — gets nixpkgs-unstable's default kernel line, whatever it happens to be on the day of nh os switch. That default moves fast: the systemd-boot entries on this machine show four different kernel builds across three days (7.1.2 → 7.1.8 → 6.18.44, generations 41–50, all built Aug 11–12). The box that's been freezing for months has never once run a kernel version chosen on purpose.

This is also the reason the crash journal is hard to act on: kernel 6.18.44 is only days old upstream when this box hit it. Fresh mainline kernels on brand-new RDNA4 hardware are exactly where an unfixed amdgpu or mm regression is most likely, and there's no way to tell "real bug" from "this specific build" without holding the kernel still.

Confidence: not that this alone causes the freeze, but that it's why the freeze can't be diagnosed further without pinning first. This is the single highest-value change on this list.

2 — OpenLinkHub is on, contrary to what the handoff assumed confirmed regression

hosts/shinobu/config/nixos-config/default.nix:11 and hosts/shinobu/users/kokoro/config/home-manager-config/default.nix:93

The handoff listed nixos-generic.desktop.openLinkHub.enable = false; under "recently applied, verify present and correct." It is not present — both the NixOS toggle and the home-manager toggle are true right now. The systemd unit still runs as root, with WorkingDirectory = /home/kokoro/code/OpenLinkHub (a plain git checkout) and ExecStart = /home/kokoro/.nix-profile/bin/OpenLinkHub — a root service executing a binary out of a path kokoro can write to, with no sandboxing (ProtectSystem, DeviceAllow, etc. are all absent) and no udev rules, because running as root just sidesteps needing any.

Per the handoff, OpenLinkHub logged nothing during the Aug 12 crash boot, so it's not implicated in that specific incident. But it's a root daemon doing raw HID ioctls from a user-writable path — that's a real hardening gap independent of the GPU question, and it's one more variable in the mix while you're trying to isolate a kernel bug. Worth turning off for the duration of the kernel test regardless of whether it turns out to matter.

Confidence: high that this configuration is wrong and should be fixed; low that it's the cause of the amdgpu/TTM or mm oopses specifically.

3 — The hyprland flake input is dead code, not a live mismatch ruled out as described, real risk nearby

flake.nix:14 declares it; nothing in modules/ or hosts/ references inputs.hyprland

The handoff's top concern was a nixpkgs.follows mismatch on the Hyprland input causing Mesa/libdrm skew. I traced every consumer: programs.hyprland.enable = true (NixOS) and wayland.windowManager.hyprland.package = pkgs.hyprland (home-manager) both pull from the plain nixpkgs input — never from inputs.hyprland. The flake input exists, has its own unfollowed nixpkgs pin (flake.lock node nixpkgs_3), and is entirely unused. It's a red herring today, but it's exactly the kind of thing that causes this failure mode the moment someone wires it in later without adding follows. Recommend deleting it outright.

The real version-skew risk is architectural, not a bug: home-manager here is standalone (modules/nixos/desktop/home-manager/default.nix only installs the home-manager CLI — it never imports home-manager.nixosModules.home-manager). System Mesa/amdgpu userspace and the user's Hyprland/wlroots are two independently built closures that only agree today because both read the same nixpkgs flake input. If nh os switch and the home-manager activation are ever run against different checkouts of flake.lock, they will drift — same symptom the handoff worried about, different cause.

Confidence: high that the specific follows-mismatch theory doesn't apply to the current repo; medium that the standalone-HM architecture is worth tightening as a preventative measure.

4 — Broken inputs.nixpkgs-unstable reference landmine, currently inert

overlays/default.nix:18

Today's b103628 "flake upgrades" commit deleted the nixpkgs-unstable flake input, but overlays/default.nix's unstable-packages overlay still does import inputs.nixpkgs-unstable {...}. Nothing in the repo currently reads pkgs.unstable, and Nix's laziness means the broken thunk is never forced — so evaluation still succeeds today. The moment anyone references pkgs.unstable.anything, the build hard-fails with a missing-attribute error. Zero risk to clean up now.

Confidence: certain — verified both the missing input and the absence of any consumer.

5 — hosts/shinobu/hardware-configuration.nix is a placeholder stub hygiene

hosts/shinobu/hardware-configuration.nix — entire file is a comment: "Paste in your hardware configuration for host: shinobu"

This was never populated by nixos-generate-config. Filesystems are covered by disko, so the machine boots fine, but there's no explicit boot.initrd.availableKernelModules/kernelModules for this host — it's relying entirely on systemd-stage1's automatic module loading. That's a normal, supported mode in current NixOS, so I'm not treating this as a freeze cause. AMD microcode updates are also not explicitly enabled anywhere, but recent nixpkgs defaults hardware.cpu.amd.updateMicrocode to hardware.enableRedistributableFirmware (which shinobu sets to true), so this is very likely already on — worth a one-line confirmation, not a fix.

Confidence: low relevance to the crash; flagging for completeness since the handoff asked for a full orientation pass.

§4

What this doesn't touch

hardware.graphics is minimal and clean on every host (just enable + enable32Bit, no ROCm/VA-API extras). No boot.kernelParams or extraModprobeConfig touch amdgpu anywhere. pkgs/default.nix is empty — no custom packages, no patched kernel, no out-of-tree modules. RAM, EXPO, and the NVMe were already ruled out before this review started and nothing found here reopens them. If the kernel pin doesn't stop the freezes, the honest next suspect is the hardware itself — the 9700X's memory controller under real load, or the un-flashed BIOS — not this configuration.

§5

Test plan

The single most informative thing you can do next, in order.

  1. Reboot now, into generation 41 (kernel 7.1.2). It's still a live systemd-boot entry (nixos-3eddc8eb8e0684...conf) and its store path hasn't been garbage-collected — confirmed both just now. This was the last generation that didn't hang and predates the run of oopses. You don't need to change the flake to try it; just pick it from the boot menu.
  2. Run several days on 7.1.2 before touching anything else. If it holds, the kernel is confirmed as the variable and you pin to a build in that family (or the closest current LTS) going forward. If it still freezes, the amdgpu/mm hypothesis is wrong and the RAM/IMC/BIOS angle moves back to the top.
  3. Apply the OpenLinkHub and overlay diffs regardless of outcome. They're correct independent of what the kernel test shows, and they remove two variables from future crash journals.
  4. Once you're back on a rebuild you trust, commit the kernel pin from §3 instead of continuing to float. Bump it deliberately later, rather than getting a new kernel as a side effect of an unrelated nh os switch.
